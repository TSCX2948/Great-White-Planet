# Great White Planet 设计思想

> 本文件由开发者在软件完成后生成（需求文档第九节：帮助菜单 → 设计思想）。
> 软件「帮助 → 设计思想」会优先读取本文件。
> 当前版本：**v1.0.0**

## 一、这个软件到底在解决什么问题

学习资料通常是**碎片化**的：教材在 `book`，笔记散落在几份 Markdown，易错题记在别处。
复习时真正的困难不是「没有资料」，而是「资料太多、彼此不连通、不成主线」。

所以 Great White Planet 的职责不是「帮你记笔记」，而是：

> **把同一个书目的零散资料，整合成一条可以直接用来复习的主线。**

这件事交给 AI 做，而人负责提供原始素材和判断。

### 助手有名字：长庚

软件叫 **Great White Planet（大白星球）**，但**软件里的 AI 助手叫「长庚」**。

这两个名字不是随便起的：金星在中国古称**启明**（晨见东方）与**长庚**（昏见西方），
《诗经》里「东有启明，西有长庚」说的就是它；
而「大白」在《史记·天官书》里正是金星的星名 ——「太白者，西方之金也」。
**Great White Planet 对应「太白」，助手对应「长庚」**，
一个名字给产品，一个名字给助手。

于是有一条实现上的约束：

> **所有 AI 提示词里的自称都必须是「长庚」，不能是「大白星球」。**

这不是纯文案问题 —— 提示词里写「你是 Great White Planet 学习软件…」时，
模型会**把软件名当成自己的名字**，于是用户问「你是谁」，
它答「我是大白星球」。所以：

* 名字抽成常量 `AI_ASSISTANT_NAME = "长庚"`，7 段提示词共用一处；
* 每段提示词都补一句「用户问起你是谁时自称长庚；不要把软件名当成你的名字」；
* **并且有一条断言守住它**：遍历所有 `*PROMPT*` 常量，
  必须都含「长庚」、都不含「大白星球」。

**为什么值得为一句"称呼"写测试**：因为它属于**人设一致性**，
散落在 7 段提示词里，靠人眼看一定会漏；
而它又是用户**最先感知到**的东西 —— 助手第一句话说自己是谁。

### 一个副产品：提示词也需要"版本号"

这个需求暴露了一个通用问题：配置是**深合并**的
（用户 config.json 里的值优先于默认值），好处是用户手改的设置不会被升级冲掉；
**代价是改了默认提示词，对老用户永远不生效** ——
他们的 config.json 里早就落着旧提示词了。

解法是给默认提示词一个版本号 `PROMPT_REVISION`：

| 情况 | 行为 |
| --- | --- |
| 用户没写过 `prompts` | 直接用新默认值 |
| `prompts.revision` 落后 | **整段换成新默认值**并落盘（只动提示词） |
| `prompts.revision` 已是最新 | 一个字都不动 —— 用户想自己改就手动填当前版本号锁定 |

**通用经验**：任何"默认值 + 用户覆盖"的配置体系，
都需要一个**默认值版本号**，否则改了默认值只能靠用户手工删配置。

## 二、三条基本原则

### 原则 1：磁盘就是数据库

科目、书目、笔记、易错题、总结全都是普通文件夹和 Markdown 文件。软件只是一个
「读得懂这些文件夹」的界面。

带来的好处：

* 可以用任何编辑器改内容（软件坏了也不丢资料）；
* 可以用网盘/移动硬盘同步和备份；
* 可以手工整理文件夹，软件刷新一下就能识别；
* 不需要数据库迁移，也不需要担心版本升级破坏数据。

代价是必须把「文件放在哪」定义得非常清楚——这就是下面这套约定的意义。

```
data
├── boxes.json                     收纳箱分组（属于用户的数据组织方式）
├── schedule.json                  「其它日程」（跨科目，见原则 4）
├── user data                      用户自己的内容
│   └── subjects
│       ├── .boxes/                收纳箱卡片图片（隐藏目录，不会被当成科目）
│       └── <科目文件夹>            一个文件夹 = 一个科目
│           ├── subject.json        科目元数据（名称/颜色/图片/类型/排序）
│           └── <书目文件夹>        一个文件夹 = 一本书（结构由科目类型决定）
│               ├── Introduct.md        简介与学习目标（参与总结）
│               ├── <书名>_summary.md   AI 生成的学习文档
│               ├── book                教材（不参与总结）
│               ├── error-prone         易错题与易错内容（参与总结）
│               ├── notebook            笔记（参与总结）
│               ├── homework            作业（不参与总结）
│               │   └── <作业名>/       一个作业一个文件夹
│               │       ├── homework.json   DDL + 提交方式
│               │       └── <作业名>.md     作业内容
│               ├── others              其它文件（不参与总结，可自建子文件夹）
│               └── book.json           书目元数据
└── else data                      软件产生的数据（不属于用户内容）
    ├── config.json                配置（可直接编辑）
    ├── secrets.json               API Key（与配置分离）
    ├── background/                主界面背景图库
    ├── summary_backup/<科目>/<书目>/<时间戳>/   总结的上一版
    ├── assets/subjects/<科目>/     科目卡片图片
    ├── chats/                     AI 聊天记录
    ├── cache/scan_cache.json      扫描缓存
    └── logs/                      运行日志
```

**为什么把用户数据和软件数据分开？**
用户数据是「绝不能丢、随时可能手工搬走」的东西；软件数据是「丢了也没关系、
可以重建」的东西。分开之后，备份只需要复制 `user data`，
而清理缓存、清空聊天记录、换背景图永远不会碰到用户内容。

**为什么天气要放后台线程、还要"可取消"？**

天气是**锦上添花**的信息，绝不该影响软件可用性：

* 这些免费接口在慢网络下要 5～20 秒才回来。放主线程会把界面冻住，
  所以放 ``QThread``；
* 但 ``QThread.quit()`` 对**阻塞在 socket 上**的 ``urlopen`` 是无效的 ——
  线程会一直挂到超时为止；如果在它还在跑的时候析构 QThread，
  Qt 会打印 ``QThread: Destroyed while thread is still running``，
  进程退出时甚至**直接段错误**（实测崩过）。
  因此请求改用**短超时分片轮询**（每 0.4 秒一片），片与片之间检查一次
  取消标志：关窗时整个查询能在 1 秒左右干净收尾；
* 另外设**总预算**（``TOTAL_BUDGET``）与**分接口超时**，
  任何一个接口卡住都不会拖住整条流程，超时就用"天气获取失败"收尾 ——
  用户看到的是灰色小字，不是转圈。

**为什么日程（`schedule.json`）不与作业存在一起？**

两者性质不同：**作业天生属于"某科目的某本书"**，所以它的 DDL 与提交方式跟着
作业文件夹走（`homework.json`），换电脑、整个搬走都不会丢。
**其它日程不属于任何科目**（"交学费"、"报名截止"），挂在某门课下反而别扭。

首页右侧那一栏是**跨科目视图**，要同时列出不同科目、不同书目的作业。
如果日程散落在各书目里，凑齐一栏就得扫描整棵树；放在数据根目录一次读完即可
—— 这也是它和 `boxes.json` 同级的原因。

**为什么"完成"状态存在作业自己身上，而不是另建一个索引文件？**

`homework.json` 里多一个 `done` 字段，好处是：**状态跟着数据走**。
用户把作业文件夹改名、搬到别的书目、整个拷到另一台电脑，完成状态都还在；
索引文件则会在这些操作后对不上号。日程同理（`schedule.json` 里的 `done`）。

**科目类型为什么用"一张表"而不是继承？**

日记 / 校修课 / 自学课的差别只有三件事：**Book 的目录清单、界面标签、
参与 AI 的目录**。因此它们在 `constants.py` 里是一张声明表
（``BOOK_TABS_BY_TYPE`` / ``template_dirs_for_type`` / ``summary_sources_for_type``），
不是三套类。加一种新类型只需要在表里加一行，"自学课的作业叫练习"也只是
同一个 `homework` 目录换个标签 —— **目录语义不分叉，界面用词才分叉**，
这样数据层、AI 层、剪贴板、导入导出全都不用知道有"类型"这回事。首页可以把几个科目收进一个箱子，但**文件一个都不动**：科目仍然是
`subjects/<科目>` 下的普通文件夹，箱子只存在 `boxes.json` 里记下"谁属于谁"。
这样删掉箱子等于删掉一条记录，科目自然回到最外层，**不存在"删箱子误删资料"的可能**。
反过来，用户手工在资源管理器里删掉科目文件夹，箱子里的失效记录会被自动清理。
这是"磁盘就是数据库"原则的直接推论：**能推导出来的关系不复制，需要用户表达的
关系才落盘**。

**收纳箱为什么只是"一层分组记录"？**

**为什么图片不放进用户数据？**
需求文档第十节明确要求。卡片图片与背景图是界面装饰，属于软件数据；
而资料里的图片属于内容，跟随原文件放在 `notebook`/`error-prone` 里。

### 原则 2：界面由扫描结果生成

代码里**不写死任何科目名、书目名、文件类型**。
`Library.subjects()` 扫描 `subjects` 目录，每个子文件夹就是一张卡片；
每个书目里的 `book`/`error-prone`/`notebook`/`homework`/`others` 就是分类标签。

标签与目录的对应关系用**声明式表格**描述（`core/constants.py` 的
`BOOK_TABS_BY_TYPE`），所以"加一个栏目"只是加一行数据，
不需要改视图、数据层或 AI 层 —— 「其它文件」就是照这个方式加的：

```python
("others", "其它文件", OTHERS_FOLDER),      # 自学课 / 校修课各加一行
```

参与 AI 总结的目录由 `SUMMARY_SOURCE_DIRS` 单独声明，
新栏目只要不写进去就**天然不参与总结**，不依赖任何"排除逻辑"。

因此：

* 新建科目 = 新建文件夹（软件帮你建，也可以自己建）；
* 删除科目 = 删除文件夹（默认走回收站）；
* 想支持新的资料格式，只需要注册一个「读取器」，界面、数据层、AI 层都不用改。

这是「支持后续修改和功能扩展」（需求文档第十一节）的落地方式：
**扩展点写在注册表里，而不是散在条件判断里。**

| 扩展点 | 位置 | 加东西的方式 |
| --- | --- | --- |
| 文件类型 | `services/document_reader.py` | `register_reader({".epub"}, my_reader)` |
| AI 提供方 | `ai/providers/*.py` | 新建文件 + `@register_provider` |
| 配置项 | `core/config.py` 的 `DEFAULT_CONFIG` | 加一个键，代码用 `config.get("a.b")` 取 |
| 提示词 | `config.json` 的 `prompts` 段 | 直接改 JSON，或在设置界面改 |
| 主题样式 | `services/themes.py` | 改配色/QSS，逻辑不动 |
| 书目页分类 | `core/constants.py` 的 `BOOK_TABS_BY_TYPE` | 加一行 `(key, 标签, 目录)` 即可多一个栏目 |
| 数据位置 | `config.json` 的 `paths` 段 | 整个数据根目录可以搬到别的磁盘 |

### 原则 3：整合，而不是概括

`<书名>_summary.md` 不是摘要，而是一份**完整的学习文档**：

* 把 `Introduct.md`（目标）+ `notebook`（笔记）+ `error-prone`（易错题）合并；
* 补全缺失的推导、定理条件、常见陷阱与辨析；
* 把易错题转成「错误表现 → 根本原因 → 正确做法 → 同类变形」的清单；
* 资料冲突或信息不足时，**列进「待确认问题」而不是编造**；
* 资料过长时，先分块提炼再合并成文，避免超出模型上下文。

这里有一个明确的取舍：**准确性优先于美观和便捷**（需求文档第五节）。
扫描件 PDF 如果无法可靠识别文字，就不猜内容，而是把页面转成图片插进文档，
让人或支持视觉的模型自己看。

## 三、分层与依赖方向

```
ui  ──────────────►  ai  ──────────►  core
 │                    │                ▲
 └──►  services  ──────┴────────────────┘
 │                    │
 └──►  data_manager  ─┘
```

| 层 | 职责 | 明确不认识 |
| --- | --- | --- |
| `core` | 配置、路径、事件、日志 | 任何业务概念 |
| `data_manager` | 扫描与增删改科目/书目 | Qt、AI |
| `ai` | 提供方适配、总结引擎、聊天会话 | Qt（除 `worker.py`） |
| `services` | 文档解析、渲染、导出、剪贴板、背景、系统集成 | 科目/书目的业务含义 |
| `ui` | PyQt6 界面 | 具体如何调用 AI、如何解析 PDF |

三条具体做法保证这个方向不被破坏：

1. **数据层、AI 层、服务层都不 import Qt**（`ai/worker.py` 是唯一例外，它专门负责线程与信号）。
   因此 `tests/smoke_core.py` 可以在没有 PyQt6 环境变量的情况下跑核心逻辑。
2. **AI 层和界面层通过事件总线通信**（`core/eventbus.py`）。
   界面订阅 `SUBJECTS_CHANGED` / `AI_FALLBACK` 等事件，而不是被数据层直接调用。
3. **惰性导入**：`gwp/services/__init__.py`、`gwp/ai/__init__.py`、`gwp/ui/__init__.py`
   只在真正用到某个子模块时才加载它，启动更快，也避免模块互相导入。

服务层的几个「纯逻辑」模块值得单独一提——它们都不依赖 Qt，所以能单独测试：

| 模块 | 职责 | 为什么独立 |
| --- | --- | --- |
| `document_reader.py` | 把各种格式变成 Markdown | 扩展格式只改这里 |
| `markdown_renderer.py` | Markdown → HTML | 预览与导出共用 |
| `pdf_exporter.py` | Markdown → PDF（含切页、页码） | 导出流程复杂，要能单独验证 |
| `page_range.py` | 解析 `1-3, e-1` 这类页码范围 | 校验规则多，必须能穷举测试 |
| `file_clipboard.py` | 复制/剪切/粘贴，含系统剪贴板互通 | Windows API 调用要能单独调 |
| `background.py` | 背景图库与命名规则 | 命名规则要能穷举测试 |

## 四、AI 的可插拔设计

### 适配器协议

所有 AI 提供方都实现同一个基类 `BaseAIAdapter`，最少只需要实现 `complete()`；
能流式输出就再覆盖 `stream()`。基类统一负责：

* 读取配置与 API Key（环境变量 → `secrets.json` → `config.json`）；
* 超时、重试、异常归一化（网络/鉴权/限流/配置错误分成不同异常类）；
* **提问机制**：把 AI 回答里的 `gwp:ask` 块从正文里剥离，变成界面弹窗，
  用户回答后自动追加进对话继续下一轮；
* **诊断钩子**：子类可实现 `diagnose()` 给出针对性排查提示，
  基类的 `test_connection()` 会自动优先使用它。

### 为什么用「提问块」而不是「函数调用」

需求文档要求「AI 对内容不确定时可以弹窗询问用户」。实现上有两条路：

1. Function Calling / Tool Use：需要不同厂商各自的协议，DeepSeek、OpenAI、
   本地程序的支持程度不一致；
2. 约定一种文本块，从输出流里解析：**任何能输出文本的 AI 都支持**。

选了第 2 条。约定 ```` ```gwp:ask {"question": ..., "options": [...]} ``` ``
或 `<!--GWP:ASK ... -->`，由 `QuestionBlockParser` 做流式解析——只有完整的块才会
触发弹窗，中间态不会误触发，解析失败也会把原文吐回正文而不是吞掉内容。

### 失败兜底

`AIManager.chat_with_fallback()` 按「当前 AI → 兜底链」依次尝试，
全部失败时给出**每一条失败原因**，而不是一句「调用失败」。
主 AI 失败切换成功时，会通过事件总线发出 `AI_FALLBACK`，界面弹窗提示用户
（need.md 第 6 条的要求）。

### 网页版为什么用剪贴板桥接

浏览器自动化（Playwright/Selenium）能全自动，但体积大、易被网站改版破坏、
需要额外安装。因此网页版适配器采用：

1. 把整理好的提示词写入系统剪贴板；
2. 打开对应官网；
3. 用户在网页里粘贴提问，回来把回答粘进软件。

**如果以后要全自动**，只需要新增一个 `type: web_automation` 的适配器，
`manager.py`、界面、配置界面都不用改——这正是可插拔结构的意义。

## 五、安全与可回退

任何「覆盖」操作都必须有后悔药：

| 操作 | 保护机制 |
| --- | --- |
| 重新生成总结 | 先把上一版复制到 `summary_backup`（默认只留一版） |
| 恢复历史版本 | 先把当前版本另存一份，所以恢复本身也能反悔 |
| 删除科目/书目 | 默认移入回收站（Windows `SHFileOperation`，不依赖 pywin32） |
| 剪切文件 | 先复制成功、再删除源文件；全部成功后才清空剪贴板 |
| 粘贴同名文件 | 自动改名为 `名称_1`（序号递增），永不静默覆盖 |
| 编辑 Markdown | 原子写入（先写 `.tmp` 再替换），避免写一半崩溃损坏 |
| 更换背景图 | 新图复制进图库，**旧图保留**，可随时切回 |
| 新建 Markdown | 只在书目页可用，固定落到该书的 `notebook`；首页/科目页禁用并说明原因，绝不猜位置 |
| 导出 PDF | 取消/失败时清掉半成品与临时文件，不会留下损坏的 PDF |
| 重复启动 | 同一数据目录只允许一个主窗口（`instance.lock` 记录 PID 与窗口句柄；崩溃留下的陈旧锁自动接管） |
| Win11 多桌面 | 窗口只在打开它的那个桌面显示；在别的桌面启动会弹窗说明并退出，不会静默无反应 |
| 配置写坏 | 所有配置项都有默认值，深合并后仍能启动 |
| 长任务卡住 | 耗时操作都在后台线程，并提供取消 |

三条关键顺序是刻意设计的：

1. 总结：**先生成 → 再备份 → 最后替换**，生成失败时磁盘上什么都不变；
2. 导出 PDF：**先排版 → 问用户 → 再切页编号**，因为 Markdown 在排版前没有「页」，
   而用户需要用 `e`（最后一页）来表达范围；
3. 粘贴：**先复制 → 再删源**，中途失败不会丢资料。

## 六、界面设计取舍

* **单窗口 + 独立文档窗口**：科目/书目用同一个窗口堆叠切换（类似文件管理器），
  打开文件时另开窗口，方便对照多份资料（需求文档第八节）。
* **AI 两个入口**：文档内的「AI 双栏」针对当前文件；菜单栏右上角的「AI 对话」
  是不读文件的日常对话。两者共用同一个聊天面板控件，只是 `document_path`
  一个有值一个为空——**复用而非复制**，以后改一处两边都受益。
* **不依赖 QWebEngine**：Markdown 预览用 `QTextBrowser` + 自写 Markdown→HTML，
  避免额外下载上百 MB 的 Chromium。
* **卡片自绘**：用 `QPainter` 画圆角矩形、渐变、图片遮罩，
  这样科目/书目卡片能保持一致观感，并且颜色、图片、圆角都由配置控制。
* **背景透出但内容块自带底色**：背景画在整个工作区上，内容区与页面区域透明，
  而**具体的内容块各自有不透明底色**——所以背景是从内容块之间的空隙里透出来的。
  这个取舍是试了三版才定下来的：

  * 第一版把照片当底纹铺满：深色壁纸会让整个界面看起来"变黑了"，可读性随图片变化；
  * 第二版给内容区加不透明白底并留边当外框：背景几乎看不见，等于白设；
  * 第三版让背景铺满、中间容器透明，并给**顶部标题栏**加一层半透明织带
    —— 标题栏是唯一"文字直接压在图上"的地方，给它一层底色就够了，
    其它地方由卡片和面板自己保证可读性。
* **背景图不用样式表画，而是自绘**：调试中发现一个反直觉的 Qt 行为——
  当应用样式表里存在 ``QMainWindow { background: ... }`` 时，
  中央控件的 QSS ``background-image`` 会**完全不绘制**（同一段样式换成
  ``border-image`` 就能画出来）。与其和样式表的内部规则博弈，不如用
  ``QPainter`` 自己画：填充方式（cover/contain/stretch/center）与蒙层都可控，
  缩放结果按控件尺寸缓存，拖动窗口不会重复解码。
* **一切文案中文、一切错误可读**：异常消息会直接展示给用户，
  所以 `AIError` 之类的消息都写成「人话 + 下一步该怎么办」。
* **"落点"由用户当前所处的位置决定，而不是由数据模型决定**：
  这是拖拽上传那条 bug 的教训。文件导进哪个目录，**唯一依据是"你现在在看哪一层"**，
  而不是"这个栏目登记的是哪个目录"。后者是**数据视角**，前者是**用户视角**；
  界面上凡是"操作作用于哪里"的问题，都必须用用户视角回答，
  否则就会出现"我在 `第一章` 里拖文件，它却跑到上一级"这种荒诞结果。
* **同一个数字只能有一种算法**：
  栏目标签上的数量被定义为"**点进去能看到几行**"，并且这个定义在
  三个地方**必须用同一套实现**（书目页标签、书目概览、首页统计）：
  * 笔记/易错题/教材/其它文件 → 数文件（因为子目录里的文件会铺开显示）；
  * **作业 → 数作业**（一个作业一行，内部 `homework.json` 不算）。
  这条约束是被用户报障逼出来的：作业标签显示「作业 2」而表格只有 1 行，
  原因是三处各写各的计数（有的用 `rglob` 递归、有的只列一层）。
  **"同一个概念在多处出现"时，最危险的不是算法错，而是算法不一致。**
* **AI 功能的第一原则：不可靠时宁可缺，不可编**（"图片提取为 Markdown"）。
  把图片交给 AI 转写，一定会碰到模糊、遮挡、手写潦草的情况。
  这类功能有两种失败方式：

  | 失败方式 | 后果 |
  | --- | --- |
  | 少写了内容 | 用户翻一下原图就补上了，代价小 |
  | **编了一段看着很像的内容** | 用户拿它当复习资料背下来，**代价极大且难以发现** |

  所以判定阈值全部**偏向"不可信"**：正文太短、出现"无法辨认/看不清/抱歉"、
  有 `[[无法辨认]]` 占位符、乱码过多 —— 只要沾上一条，就**直接插入原图 + 写明原因**，
  一个字都不编。这是"**默认安全**"原则在 AI 功能上的应用：
  默认选"出错影响最小"的那一边。
  另外**人始终有最终否决权**：能手动标记没把握、能改正文，
  而人手改过的内容就不再被自动判死 —— 用户看过原文，他的判断优先于任何启发式规则。
* **"一个条目一行"的列表，进入条目后必须切换成"列真实内容"**：
  作业栏目在根目录是"一个作业一行"（人读的是作业，不是文件），
  但双击进到某个作业里之后，用户要看的就是**这个文件夹里到底有什么** ——
  两者是**不同层级的视图**，不能共用同一套过滤。这是"本地有内容但软件不显示"
  那条 bug 的根因：进到作业内部还在用"作业条目"的规则过滤，结果恒为空。
  **凡是支持"进入下一层"的列表，都要在进入时切换数据来源**，
  而不是在同一份数据上换个过滤条件。
  同时，**软件自己的元数据文件（`homework.json`）也要列出来**
  ——不列用户会以为文件夹是空的；但要置灰、标注用途、并去掉改名/删除入口，
  因为它和用户可见的 DDL/提交网址之间存在**用户看不见的关联**，
  误删会造成"数据莫名其妙丢了"。
* **"上传"这个词在本地软件里要拆开理解**（AI 对话附件）。
  需求说"附件上传"，但当前 AI 是文本模型、API 收不了文件，
  照字面做就是假的。拆开之后就清楚了：用户真正想要的是
  **"让 AI 看到这个文件的内容"**，而这件事有两种实现，各有所长：

  | 类型 | 做法 | 为什么 |
  | --- | --- | --- |
  | 文档（PDF/Word/Excel/文本） | **本地提取正文** | 确定性：PDF 有文字层、docx 有结构化段落，**同一份文件每次结果一致**，比让 AI 看图猜字可靠得多；而且离线、免费、用户能自己核对 |
  | 图片 | 视觉模型，或人工粘贴 | 图片没有"可提取的文本层"，只能靠看 |

  所以最终**没有一个功能叫"上传"**，而是"文档 → 提取正文"+"图片 → 交给视觉"。
  **需求里的名词往往不是最好的设计单位**：把"用户要的结果"和
  "能用的手段"分开看，方案就自己出来了。
* **AI 看不到的东西必须说出来**（同上）。
  附件提取失败、图片没有视觉模型时，界面上**照样列出这份附件并写明原因**，
  而且会在提示词里明确告诉模型"这些内容没有给你"。
  否则用户会以为文件已经传进去了，**从而相信一个其实没读过文件的回答** ——
  这种"看起来成功了"的失败，比直接报错危险得多。
* **"关闭"不等于"退出"时，必须同时给出"退出"的明确入口**（关闭到后台）。
  需求是"主界面关闭后软件在后台运行"，理由是启动慢。
  但一旦 `✕` 的含义从"退出"变成"藏起来"，就会产生一个**新的**问题：
  用户想退出时找不到方法（只能开任务管理器 —— 用户自己都说了这句，
  但那是在描述期望，不是在要求"只能这样"）。
  所以这个特性的完整形态是**三件套**：

  | 能力 | 给谁 |
  | --- | --- |
  | `✕` = 隐藏到后台 | 让"下次打开"变快 |
  | **托盘图标**（双击唤回 / 右键完全退出） | 给用户一个看得见的回收路径 |
  | 菜单「文件 → 退出」+ 设置里的开关 | 尊重"我就想关掉"的用户 |

  **凡是把某个常用操作的含义改掉，都必须同时提供它原来的含义。**
  否则用户会觉得"这软件关不掉了"，那比启动慢糟糕得多。
  同理，`✕` 与「退出」现在走的是同一条清理链路
  （`closeEvent` 里"确认未保存文档 → 清理 → 释放资源"），
  只是靠一个 `_really_quit` 标志区分 ——**不写两份退出逻辑，两份一定会不一致**。
* **"折叠态显示什么"是数据的决定，不是界面的决定**（单词书）。
  需求是"单词卡折叠后只显示英语，单击后展开"。看上去是纯交互，
  实际上它给数据模型加了一条**硬约束**：**必须有一个字段能单独代表这张卡**，
  而且它要在折叠状态下就足够让用户认出这张卡。
  所以 `WordCard.english` 是唯一必填字段，也是唯一的折叠标题；
  其余（音标/释义/例句…）都是可选的补充。
  这样做还有一个连带好处：**新建一张卡只需要一个字段** ——
  用户"只填英文"，其余交给 AI，界面上就不需要一大张表单。
  如果反过来按"字段都要填"来设计，用户每次加词都要填七八个框，
  "自动补齐"这个需求本身就不成立了。
  **交互需求经常在悄悄规定数据结构**，读需求时要把它翻译出来。
* **"没抛异常"不等于"成功了"**（`cmd /c` 那个 bug）。
  用 `Popen` 启动外部程序，只要系统能把进程创建出来就返回成功 ——
  哪怕那个进程**立刻失败退出**。
  VSCode 的 `cmd /c` 调用正是如此：`cmd` 打印一句
  `'D:\VS' is not recognized ...` 就退出了，而软件返回了 `True`、
  界面上什么都没提示，**表现为"点了没反应"**。
  这类"成功了但没生效"的失败最难查，因为它不留痕迹。
  两条应对：
  **①能被测试断言的地方就不要靠"跑起来看看"** ——
  所以我把命令行拼接抽成了 `vscode_command()`，测试直接断言
  "第一个参数不是 cmd、命令只有两个参数"；
  **②只在人看得见的地方做"尽力而为"** ——
  外部程序启动成功与否本来就无法从返回值判断，
  那就把**日志**写清楚（"已用 VSCode 打开：…（编辑器=…）"），
  出问题时至少有一条线索。
* **只在"某个环境条件下"才出现的 bug，必须在那个条件下构造测试**
  （同上）。这个 bug 只在**安装路径含空格**时出现，而我在
  `C:\Users\...\Temp\` 里测试，一直是好的。
  所以回归测试里我**刻意用 `D:\VS Code\bin\code.CMD` 这个带空格的路径**
  来构造命令 —— 用一个"干净"的路径去测，等于没测。
* **同一份数据在两处显示，"刷新"要覆盖全部显示**（删除后跳回上一层）。
  用户报的"删除文件后返回上一层"，根因不是删除逻辑，
  而是 `refresh()` 只重填了**各标签的根目录列表**，
  没有重画**"当前所在文件夹"**这个第二层视图。
  值得注意的是：`_current_folder`（位置状态）和标题**一直是对的**，
  只有表格内容错了 —— 所以现象是"位置没变、但东西变了"，
  很容易被误判成"刷新时机不对"。
  **当一个状态在界面上有两处体现时（这里是标题 + 表格），
  刷新只更新了其中一处，就会产生"自相矛盾"的界面。**
  修法是在 `refresh()` 的末尾统一收口：如果在文件夹里，
  就重画那个文件夹 —— 这样**所有**走 `refresh()` 的操作
  （删除/重命名/导入/拖拽/新建文件夹）一次全覆盖，
  而不是在每个操作后面各补一句。

## 七、已知边界

诚实列出，便于后续升级：

1. `.doc`/`.ppt`/`.xls`（2003 旧格式）不能直接解析，需先另存为新格式；
2. 图片型 PDF 不做 OCR，只按图片插入（准确性优先的必然结果）；
3. PDF 表格跨页时可能从中间断开（PyMuPDF `Story` 的限制），且没有页眉/页脚文字；
4. 从 Markdown 导出 PDF 时需要**先排版**才能知道页数，因此首次导出多一步排版耗时
   （已通过"复用排版结果"避免二次排版）；
5. 一个书目对应一个 summary 文件，不支持同一本书生成多个版本的总结（版本靠备份管理）；
6. 聊天记录是「关闭软件即清空」（需求文档要求），不做跨会话记忆；
7. 只做了 Windows 平台的开机自启、快捷方式与系统剪贴板互通。

以上每一条都是**独立模块的替换**，不影响其它部分——这就是分层与可插拔的回报。
